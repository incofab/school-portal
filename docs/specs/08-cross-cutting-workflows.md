# Cross-cutting workflows

## Institution page workflow

```text
/{institution}/...
  -> RouteServiceProvider institution group
  -> institution.user + auth + web middleware
  -> Institution::resolveRouteBinding
  -> VerifyInstitutionUser
  -> controller role/permission/ownership checks
  -> scoped Eloquent query + UITableFilters + pagination
  -> Inertia page props
  -> DashboardLayout + shared components
```

For a new institution page, confirm all of the following: route name starts with the existing `institutions.` namespace, the route is in the right included file, the controller is under `Institutions`, institution-scoped models are used, access is enforced server-side, and the page uses `useInstitutionRoute()` plus the existing dashboard shell.

## Student create/update example

`routes/institution.php` maps student resource routes to `Staff/StudentManagementController`. The React page is `pages/institutions/students/create-edit-student.tsx`; it uses `useWebForm`, shared user/student controls, a classification selector, a toast, and an Inertia visit after success. The Action `RecordStudent` creates/updates the `User`, institution membership, default institution role, and `Student` record. The feature test `tests/Feature/Actions/RecordStudentTest.php` verifies the relationships and generated code. A similar change should inspect that route/controller/page/Action/test chain before adding another student workflow.

## Result recording example

The course-result pages submit to staff result controllers. `RecordCourseResult` enriches the request with course teacher/course/class/teacher identity, checks result locking, resolves assessment values and dependencies, computes grade, upserts `CourseResult`, emits academic-integrity audit data, and optionally evaluates the class. The result aggregates then feed term/session processing and report/result-sheet pages. The relevant tests under `tests/Feature/Actions/CourseResult` and `Http/Controllers/Institutions/Staff` are the executable business specification.

## Media upload example

Curriculum pages submit one file to a named media route. The controller validates with `CurriculumMediaRequest`, delegates storage to `CurriculumMediaService`, which uses the institution folder and media subsystem, and returns JSON. The page updates or reloads its attachment list. Tests use `Storage::fake('s3_public')`, fake uploaded files, database assertions, and storage existence/missing assertions. Reuse `MediaManager`, `HasMedia`, `Media`, and `S3Folder` instead of writing raw provider paths.

## Filtered list workflow

1. The controller starts an Eloquent query and passes request data to the matching `UITableFilters` class.
2. It eager-loads the relations rendered by the page and calls `paginateFromRequest()`.
3. The page renders `ServerPaginatedTable`, declares `validFilters`, and opens a module-specific filter Drawer.
4. The Drawer writes URL query keys; pagination/sort also update the URL with Inertia.
5. A follow-up request repeats the server filter path, so filters must have consistent backend/frontend key names.

## File/export workflow

Downloads may be generated by an Action/controller using PHPSpreadsheet, DOMPDF, a Blade view, or a React/browser utility. The route and page tell you which. Use explicit download routes/anchors for files, keep institution scoping on generated records, and cover headers/content or storage behavior in tests where practical.

## Payments and settlement workflow

Public or institution payment pages create payment references through a processor/merchant flow. Provider webhooks verify and confirm references. Institution finance pages expose fee payments, receipts, manual payments, and payment attempts. The scheduled settlement command selects eligible confirmed/unsettled records, groups them by institution, creates settlements and withdrawals, and leaves failed institutions retryable. Do not assume a provider callback is the same as a completed settlement.

## Messaging workflow

Controllers/actions record a `Message` and recipients, resolve the channel/contact, apply institution message charging where applicable, and dispatch through `MessageDispatcher` or a queued provider job. SMS compliance validation, provider retryability, and `MessageStatus` updates are handled in the messaging service/job layer. Keep provider secrets and raw recipient payloads out of audit/log output.

## Assistant workflow

The assistant can be public/guest, authenticated shared, or institution-scoped. Conversations and messages use Laravel AI models plus project extensions. Institution read tools are registered in `AssistantToolRegistry`; write-capable tools are in `AssistantActionRegistry`. Write actions create an `AssistantActionExecution` preview and require confirm/cancel routes, idempotency, token hashing, and actor/institution context. Diagnostics are manager-admin only and use assistant metrics.

## Shared settings and academic context

`SettingsHandler::makeFromRoute()`/`makeFromInstitution()` reads institution settings such as current term/session, mid-term behavior, result settings, activation requirements, PIN usage, lock state, full-name format, attendance notifications, and preferred message channel. `HandleInertiaRequests` shares current term/session and settings-derived frontend values through `useSharedProps()`. When adding academic UI, use these shared settings rather than fetching or hardcoding a parallel context.
